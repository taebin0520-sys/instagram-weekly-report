# Requirements — 아벤투라 인스타 주간 리포트 (브랜드 강화 기준)

## 1. 목적

아벤투라협동조합의 인스타그램 게시물 성과를 **수기 입력 CSV** 하나로부터
**주간 텍스트 리포트**로 변환한다.

카드뉴스는 판매용이 아니라 **협동조합 브랜드 홍보용**이다.
따라서 리포트가 답해야 하는 질문은 "몇 명이 문의했나"가 아니라
**"이번 주 콘텐츠가 사람들 기억에 남았나"** 이다.

이 목적이 지표 우선순위를 결정한다.

| 순위 | 지표 | 정의 | 역할 |
|---|---|---|---|
| 1 | 저장률 | 저장 / 도달 | 브랜드 각인 핵심 지표 |
| 2 | 참여율 | (좋아요+댓글+저장+공유) / 도달 | 전반적 반응 |
| 3 | 공유 수 | shares | 확산 |
| 참고 | 문의·신청 | dm_inquiries, signups | **스터디모집 게시물에서만** 의미 있음 |

## 2. 용어 정의

- **주(week)**: ISO 8601 주 (월요일 시작, 일요일 종료). `(ISO year, ISO week)` 쌍으로 식별.
- **이번 주**: CSV에 존재하는 가장 마지막(최신) 주.
- **지난주**: 이번 주의 ISO 주 번호 -1에 해당하는 주. 달력상 직전 주를 의미하며,
  "CSV에 있는 두 번째로 최신인 주"가 아니다. (공백 주를 건너뛰어 비교하면 왜곡)
- **확인 불가**: 계산에 필요한 값이 없거나 분모가 0이어서 **수치를 산출할 수 없는 상태**.
  0%, `-`, `N/A`, 임의 추정치와 명확히 구분된다.
- **percentage point**: 비율 지표의 증감 단위. 리포트 표기는 **`%p`**.
  1.4% → 1.5%는 `+0.1%p`. (절대 수치의 증감은 `%p`가 아니라 `%`로 표기한다 — R4.2)

## 3. 입력 데이터 계약

파일: CSV, UTF-8, 헤더 1행. 1행 = 게시물 1건.

| 열 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `date` | `YYYY-MM-DD` | ✅ | 게시 날짜 |
| `type` | 문자열 | ✅ | 카드뉴스 / 릴스 / 피드 |
| `topic` | 문자열 | ✅ | 협동조합소개 / 제품 / 후기 / 스터디모집 |
| `reach` | 정수 ≥ 0 | ✅ | 도달 (모든 비율 지표의 분모) |
| `likes` | 정수 ≥ 0 | ✅ | 좋아요 |
| `comments` | 정수 ≥ 0 | ✅ | 댓글 |
| `saves` | 정수 ≥ 0 | ✅ | 저장 |
| `shares` | 정수 ≥ 0 | ✅ | 공유 |
| `profile_visits` | 정수 ≥ 0 | ✅ | 프로필 방문 |
| `dm_inquiries` | 정수 ≥ 0 | ✅ | DM 문의 (참고 지표) |
| `signups` | 정수 ≥ 0 | ✅ | 신청 (참고 지표) |

## 4. 요구사항

### R1. CSV 로드 및 검증

**사용자 스토리**
> 운영자로서, CSV에 오타나 빈칸을 넣었을 때 리포트가 조용히 틀린 숫자를 내놓는 게 아니라
> 어디가 잘못됐는지 바로 알고 싶다.

**수용 기준**
1. 유효한 CSV 경로가 주어지면, 시스템은 위 11개 열을 가진 데이터 구조를 반환한다.
2. 필수 열이 하나라도 없으면, 시스템은 **누락된 열 이름을 모두 나열한** 오류를 발생시킨다.
3. `date`가 `YYYY-MM-DD`로 파싱되지 않으면, 시스템은 **해당 행 번호와 원본 값**을 포함한 오류를 발생시킨다.
4. 수치 열에 음수 또는 숫자로 변환 불가한 값이 있으면, 시스템은 **행 번호·열 이름·값**을 포함한 오류를 발생시킨다.
5. 파일이 존재하지 않으면, 시스템은 경로를 포함한 명확한 오류를 발생시킨다.
6. 데이터 행이 0건이면, 시스템은 "집계할 게시물이 없다"는 오류를 발생시킨다.
7. 시스템은 어떤 경우에도 **누락값을 0으로 자동 보정하지 않는다.**
   (0은 "성과가 없었다"는 실제 관측값이므로, "입력을 안 했다"와 섞이면 지표가 오염된다)

### R2. 주 단위 집계

**사용자 스토리**
> 운영자로서, 게시물을 날짜별로 기록하지만 리포트는 주 단위로 보고 싶다.

**수용 기준**
1. 시스템은 각 게시물을 `date`의 ISO 주에 배정한다.
2. 시스템은 주별로 `reach`, `likes`, `comments`, `saves`, `shares`, `profile_visits`,
   `dm_inquiries`, `signups`의 **합계**와 게시물 건수를 산출한다.
3. 시스템은 CSV에 존재하는 최신 주를 "이번 주"로 선택한다.
4. 주 경계는 CSV 입력 순서와 무관하다. (정렬되지 않은 CSV도 동일 결과)

### R3. 핵심 지표 계산

**사용자 스토리**
> 운영자로서, 브랜드 각인이 잘 됐는지 저장률로 먼저 확인하고 싶다.

**수용 기준**
1. `reach > 0`이면, 시스템은 `저장률 = saves / reach`를 계산한다.
2. `reach > 0`이면, 시스템은 `참여율 = (likes + comments + saves + shares) / reach`를 계산한다.
3. 시스템은 주 전체 합계 기준 지표와 **게시물 개별 지표**를 모두 산출한다.
4. 비율은 리포트에서 **소수점 1자리** 백분율로 표시한다. (예: `1.5%`)
   팀원 공유용 리포트이므로 가독성을 우선하며, 표본이 작아 2자리는 실질적 의미가 없다.
5. **`reach == 0`이면 시스템은 해당 지표를 "확인 불가"로 산출한다. 0%로 표시하지 않는다.**

### R4. 전주 대비 비교

**사용자 스토리**
> 운영자로서, 이번 주가 지난주보다 나아졌는지 한 줄로 알고 싶다.

**수용 기준**
1. 이번 주와 지난주의 **비율 지표**(저장률·참여율)가 **모두 산출 가능**하면,
   시스템은 두 값의 차이를 `%p` 단위로 표시한다. (예: 저장률 1.4% → 1.5% = `+0.1%p`)
2. **절대 수치**(도달, 저장, 공유 등)의 전주 대비는 **상대 증감률을 `%`로** 표시한다.
   비율이 아닌 값에는 `%p`를 쓰지 않는다. (예: 도달 3,270 → 3,050 = `-6.7%`)
3. **지난주 데이터가 CSV에 없으면, 시스템은 모든 전주 대비 항목을 "확인 불가 (지난주 데이터 없음)"으로 표시한다.**
4. **지난주 `reach == 0`이면, 해당 비율 지표의 전주 대비는 "확인 불가"로 표시한다.**
5. 시스템은 전주 대비를 계산할 수 없을 때 **이번 주 절대 지표는 그대로 표시한다.**
   (비교 불가 때문에 리포트 전체가 비는 일은 없어야 한다)

### R5. "확인 불가" 처리 — 최우선 규칙

**사용자 스토리**
> 운영자로서, 데이터가 없는 칸에 0%가 찍혀 있으면 "성과가 나빴다"고 잘못 읽게 된다.
> 모르는 건 모른다고 나와야 한다.

**수용 기준**
1. 다음 경우 지표는 "확인 불가"다.
   - 분모(`reach`)가 0
   - 지난주 주 데이터 자체가 없음
   - 비교 대상 중 한쪽이 이미 "확인 불가"
2. 시스템은 "확인 불가"를 **0, 0.0, `-`, 빈 문자열, `nan`으로 대체하지 않는다.**
3. 리포트 출력 문자열은 정확히 `확인 불가`이며, 사유가 있으면 괄호로 덧붙인다.
   (예: `확인 불가 (도달 0)`, `확인 불가 (지난주 데이터 없음)`)
4. "확인 불가"는 계산 단계에서 **전파**된다. 중간에 0으로 눌러서 계산을 이어가지 않는다.

### R6. 지표 우선순위 표시

**사용자 스토리**
> 운영자로서, 리포트를 위에서부터 읽으면 중요한 순서대로 보이길 원한다.

**수용 기준**
1. 리포트는 **저장률 → 참여율 → 공유·도달 → 참고 지표** 순서로 출력한다.
2. 문의·신청은 **"참고 지표" 라벨이 붙은 별도 구획**에만 출력한다.
3. 문의·신청은 `topic`이 `스터디모집`인 게시물 기준으로 집계해 표시하고,
   그 외 게시물의 문의·신청은 **핵심 성과로 해석하지 않는다**는 문구를 함께 출력한다.
4. 문의·신청 수는 전체 성과 요약 문장이나 상단 헤드라인에 등장하지 않는다.

### R7. 리포트 출력

**사용자 스토리**
> 운영자로서, 실행하면 바로 복사해서 팀에 공유할 수 있는 텍스트가 나오길 원한다.

**수용 기준**
1. 시스템은 리포트를 표준 출력(stdout)에 플레인 텍스트로 출력한다.
2. 리포트는 대상 주의 기간(시작일~종료일)과 게시물 건수를 머리말에 포함한다.
3. 리포트는 이번 주 게시물별 저장률·참여율 표를 포함한다.
4. 리포트는 **저장률 기준 상위 게시물**을 "잘 된 콘텐츠"로 지목한다.
5. 리포트는 마지막에 **비어 있는 "다음 주 액션" 칸**을 포함한다.
   (자동 생성하지 않는다 — 판단은 사람이 한다)
6. 리포트는 목표 수치를 자동 생성하지 않는다. 항상 실제 입력값만 사용한다.

### R8. 실행 진입점

**수용 기준**
1. `python main.py <csv_path>`로 실행된다.
2. 인자가 없으면 사용법을 출력하고 0이 아닌 종료 코드로 끝난다.
3. 검증 오류가 발생하면 스택 트레이스가 아니라 **읽을 수 있는 오류 메시지**를 출력하고
   0이 아닌 종료 코드로 끝난다.

### R9. 테스트

**수용 기준**
1. 계산 로직(`src/kpi.py`)은 pytest로 검증된다.
2. 테스트는 최소한 다음을 덮는다.
   - 정상 저장률·참여율 계산
   - `reach == 0` → "확인 불가"
   - 지난주 없음 → 전주 대비 "확인 불가"
   - 전주 대비 pp 계산 정확성
   - 주 경계 배정 (ISO 주)
3. 기존 테스트는 깨지지 않는다. 변경 후 반드시 `pytest` 재실행으로 확인한다.

## 6. 미확정 사항 (사용자 확인 필요)

1. **기존 코드 부재** — 워크스페이스에 `src/`, `main.py`, `tests/`가 없다.
   README가 설명하는 구조만 확인된 상태. 개선 작업 전에 원본 코드 확보가 필요하다.
2. ~~**주 정의**~~ — ✅ **확정 (2026-09-25, 사용자 확인)**: 주 경계는 **ISO 주, 월요일~일요일** 기준이다.
   조합 내부에 별도 기준은 없다. 2절 용어 정의대로 진행한다.
3. **`profile_visits` 위치** — 브랜드 관심의 선행 지표로 볼 수도, 참고 지표로 볼 수도 있다.
   현재는 "핵심 3순위 아래, 참고 지표 위"로 배치했다.
4. **저장률 벤치마크** — "좋은 저장률"의 기준선이 없다. 절대 판정 대신 전주 대비만 표시한다.
