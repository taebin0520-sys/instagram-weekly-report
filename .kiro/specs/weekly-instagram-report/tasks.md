### T5. ④ 주 경계를 ISO(월~일)로 교정

**왜 먼저 하는가** — "이번 주가 어디까지인가"가 바뀌면 그 위에 올라가는 모든 수치가
바뀐다. 단위·순서를 먼저 고치면 나중에 다시 검산해야 한다. **토대부터 맞춘다.**

**대상**: `src/data_loader.py`

1. `split_by_week()`의 `strftime("%Y-W%U")` → **`strftime("%G-W%V")`**
   - `%V` = ISO 주번호(월요일 시작), `%G` = ISO 주 기준 연도
   - `%Y` + `%V` 조합은 연말에 깨지므로 **반드시 `%G`** 를 쓴다
2. "지난주"를 `weeks[-2]` → **이번 주 월요일 − 7일**로 계산.
   그 키가 데이터에 없으면 `None` (→ 확인 불가)
3. `week_bounds(week_df)` 함수 **추가** — 그 주의 월요일·일요일 반환
4. `report.build_weekly_report()`의 기간 표시를 게시물 최소/최대 날짜 →
   `week_bounds()` 결과로 교체

**검증**
- CI `6 passed` (이 함수들은 기존 테스트 대상이 아님 → 영향 없어야 정상)
- smoke 출력 기간이 `2026-10-06 ~ 2026-10-09` → **`2026-10-05(월) ~ 2026-10-11(일)`**
- 집계 대상 게시물은 4건 그대로 (샘플 데이터는 묶음 결과가 동일)

**주의** — 샘플 데이터에는 일·월요일 게시물이 없어서 **주 분리 결과 자체는 안 바뀐다.**
라벨과 기간 표시만 바뀐다. 즉 "고쳐도 출력이 거의 같다"가 정상이며, 이 교정의 가치는
*앞으로 일요일에 게시할 때* 드러난다. 검증하려면 일요일 날짜 행을 임시로 넣어봐야 한다.

### T6. ① 전주 대비 단위 분리 (비율 `%p` / 절대 수치 `%`)

**대상**: `src/kpi.py`, `src/report.py`

1. `kpi.py`에 **`diff_pp(this_rate, last_rate)` 추가** — 비율 지표의 차이(pp).
   한쪽이라도 `None`이면 `None` 반환 (전파)
2. `week_over_week()`는 **수정하지 않는다** — 절대 수치의 상대 증감률(%)로 계속 사용
3. `report._fmt_delta()`를 **둘로 분리**
   - `_fmt_delta_pp(v)` → `(+0.1%p 전주 대비)` — 저장률·참여율
   - `_fmt_delta_pct(v)` → `(-6.7% 전주 대비)` — 도달·저장·공유
4. `None`일 때 문구를 `(확인 불가 — 지난주 데이터 없음)`으로 통일

**검증**
- CI `6 passed`
- smoke 출력에서 `총 도달 3,050 (-6.7%p …)` → **`(-6.7% …)`** (`%p` 제거)

**핵심** — 숫자는 원래 맞았고 **단위 라벨만 틀렸다.** 도달은 비율이 아니므로 `%p`가
성립하지 않는다. `diff_pp`를 새로 만드는 이유는 `week_over_week`가 baseline 테스트
대상이라 손댈 수 없기 때문이다.

### T7. ③ [이번 주 요약] 재구성 — 저장률 → 참여율 → 공유·도달

**의존**: T6 (`diff_pp`, 분리된 포맷터 필요)

**대상**: `src/report.py`

1. 요약 순서를 **저장률 → 참여율 → 공유 → 도달**로 변경
2. **주 전체 저장률을 신규 표시** (현재 요약에 아예 없음 — 규칙 4 위반)
3. 주 단위 비율을 **합계 기준**으로 계산.
   `save_rate(totals_dict)` / `engagement_rate(totals_dict)` — **기존 함수 재사용**
   (두 함수는 `row["reach"]` 같은 키 접근만 하므로 dict 도 그대로 동작한다)
4. `latest["engagement_rate"].mean(skipna=True)` 제거

**검증**
- CI `6 passed`
- smoke 출력 요약이 다음으로 바뀜
  ```
  - 저장률 1.5% (+0.1%p 전주 대비)
  - 참여율 9.0% (-0.2%p 전주 대비)
  - 공유 9건 (+0.0% 전주 대비)
  - 총 도달 3,050 (-6.7% 전주 대비)
  ```

**⚠️ 출력이 바뀐다** — 참여율 `9.1%` → **`9.0%`**.
게시물별 평균(9.0525%) → 합계 기준(9.0492%)으로 반올림 자리가 넘어간다.
합계 기준이 맞는 이유는 도달 40인 글과 4,000인 글을 같은 비중으로 평균하면
저도달 게시물이 과대 반영되기 때문이다.

**부수 효과 (규칙 3 구멍 하나가 막힌다)** — `add_rates`가 만든 열은 `None`이 섞이면
object dtype이 되고, `.mean()`이 `None`이 아니라 `nan`을 돌려줄 수 있다. 그러면
`_fmt_pct(nan)`이 `"확인 불가"`가 아니라 **`"nan%"`** 를 출력한다.
합계 기준으로 바꾸면 이 경로가 사라진다.

### T8. ② 문의·신청을 [참고 지표] 구획으로 분리

**대상**: `src/report.py`

1. `[이번 주 요약]`에서 `- (참고) 문의 N건 / 신청 N건` **줄 삭제**
2. `[주제별 평균 …]` 뒤에 **`[참고 지표 — 문의 · 신청]` 구획 신설**
3. 집계 대상을 전체 → **`topic == "스터디모집"` 게시물만**
4. 구획에 명시 문구 포함
   ```
   ※ 브랜드 홍보 목적 게시물의 성과는 저장률·참여율로 판단합니다.
      아래는 스터디모집 게시물에 한해 참고용으로만 확인하며,
      성과 판단에 사용하지 않습니다.
   ```

**검증**
- CI `6 passed`
- smoke 출력에서 요약에 문의·신청이 **없음**
- 참고 지표 구획에 **`스터디모집 게시물 1건 — DM 문의 1건 / 신청 0건`**

**주의** — 현재 표시되는 `문의 3건 / 신청 2건`은 **전체 게시물 합계**다.
스터디모집만 세면 **문의 1건 / 신청 0건**이다. 위치뿐 아니라 **집계 대상도 틀렸다.**
`topic_summary()`의 `총문의`/`총신청` 열은 출력에 쓰지 않으므로 그대로 둔다.
